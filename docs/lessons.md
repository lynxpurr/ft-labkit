# Lessons（公开版 · 按"形状"归档）

> 这些教训来自若干真实的微调与推理工程项目。去掉了项目名、日期和读数，
> 只留形状、修法与通用律。跨项目的通用规则见 [lessons-distillation.md](lessons-distillation.md)
> 的晋升管道；下面每一条都是某次真实事故的蒸馏。
>
> 记法：**判据**=检查用来判定的条件；**被检对象**=被检查的东西；**门**=机器可查的检查。

## A. 检查器与门

### A1. 判据与被检对象共享盲区

- **形状**：收尾门的正则"判决落表…（中|不中）"恰好匹配模板里的"待填（中/不中…）"占位行，
  却匹配不了真实回填的"：中（…）"——门在占位态绿、在真实态红。判分器的阴性对照只做
  幅值扰动（×0.5），对"符号写反"完全失明，恒真判分器因此存活了很久。
- **修法**：判据锚定语义位（冒号后紧跟判决词）+ "占位残留"双保险；阴性对照至少含
  幅值与符号两类独立扰动。
- **通用律**：每个门都要有"占位形态必须红、真实形态必须绿"的两侧对照单测。

### A2. 门的状态分支没被真实路径踩过 = 纸门

- **形状**：数据指纹门的通过态只在"新仓、占位注释、不计门"分支下跑过；第一个登记了
  真实条目的项目首跑即红（文件参数与工作目录双重前缀）。
- **修法**：文件参数与 cwd 同基准；补"真值绿 / 篡改红"两侧对照回归。
- **通用律**：一个门有几个状态分支，每个分支都要有真实路径踩过一次才算存在。

### A3. 存在性不等于可用

- **形状**：环境检查只看"文件在位 + 可执行位"。系统升级抽走了 venv 的底座解释器，
  可执行文件仍在，整条链在起跑时才报 bad interpreter——检查是绿的。
- **修法**：环境类检查的"绿"= 真命令冒烟通过（退出码 0），不是存在性。
- **附带**：venv 的底座解释器是隐式未钉依赖。修复 = 装回同版本解释器 + 改 venv 的
  两处指向（`bin/python` 符号链接、`pyvenv.cfg` 的 home）。

### A4. 检查命中检查者自己（自匹配）

- **形状**：`pkill -f "xxx.yyy"` 的模式串出现在执行它的 shell 自己的命令行里，
  shell 把自己杀了，后续步骤全部截断。规则写进 playbook 之后又破了两次；
  把模式串改成方括号形态后，同一命令里的 `echo` 提示文案仍是明文，照样自杀。之后
  又一次：一次只想列出相关进程的排查扫描，只排除了自己的 pid 与父进程，结果把宿主的
  包装 shell 和别的会话里含着同一关键词的命令文本一并列了出来。
- **修法**：进程名匹配用 `pgrep -f "xxx[.]yyy"` 方括号形态；`pkill -f` 禁止使用
  与执行 shell 命令行同串的模式；**整条命令行（含提示/日志文案）不许出现目标串明文**；
  排查类扫描排除整条祖先链（一直排到根），并避开命令文本里含判据词的包装进程，能按
  进程名匹配就不匹配完整命令行。
- **通用律**：文档规则挡不住"顺手一杀"——同型多次出现就该升为代码级护栏。

### A5. 模板里的"提醒性占位"会污染下游机器门

- **形状**：模板自带的指纹文件占位注释，让新仓的数据指纹门必红。
- **修法**：门对"无真实条目"显式三分（未登记=通过并提示 / 有条目全过=绿 /
  有条目失败=红）。
- **通用律**：模板里每个会进机器判定的文件，占位态与真实态都要有门读数。

### A6. 检查器自己不会变红 = 另一种纸门

- **形状**：四种"看着像通过"的空结果。①一层 `grep` 包装转发时丢掉了 stderr、
  还按 `.gitignore` 跳过被忽略的文件——搜不到也不报错，读数是 0；②密钥扫描器在
  git 仓库之外不扫任何文件，种了假密钥也报 0；③发布前的信息盘点取不到要对比的
  全集，两项悄悄变成空集，报告仍然是绿的；④拿页面上的几行字当"开关已开"的指标，
  用已知开、已知关的样本一对，才发现那几行字取决于各仓库自己的文档，与开关无关。
- **修法**：每条判据带阳性对照——必须命中一段合成样本才算数，否则报错退出，不许
  静默空结果；判据的输入全集非空，取不到即报错，不悄悄变小；把别的东西（页面文字、
  日志行数、文件存在）当指标读之前，先用两侧样本验过它跟着被测对象变。
- **通用律**：没见过它变红的检查器，等于没测过；验不了的那一面如实写"未实测"。
  报告里常驻的非零读数同理——要么查明并修检查器，要么写成具名豁免，不许带着
  未定性的命中过门（见 A8）。

### A7. 遍历工作树的检查器撞上被忽略的缓存

- **形状**：测试跑过之后，工作树里多了被 `.gitignore` 覆盖的字节码缓存目录。
  一个发布检查器遍历整棵工作树，读到缓存文件时解码失败，整个检查崩掉、不给任何
  判定；另一个项目的发布检查器在同一个地方崩过。此前没出事，只是那些克隆里
  恰好没有缓存。
- **修法**：只遍历 `git ls-files` 列出的文件（要清就先 `git clean -ndX` 看一遍再清）；
  被跟踪的文件无法解码时交给专门的检查项判红，不让它把整个检查带崩。

### A8. 常驻的非零读数被当成背景噪声

- **形状**：一份盘点报告的同一类里，自第一批起每一份都带着同一处命中。它不在
  "必须为 0"之列，于是每一批都带着它过门，没有人查明它匹配到了什么。查明后：
  仓库 README 里的一个英文单词，恰好与 systemd 列表里一条 `not-found` 的占位行同名——
  那台机器上并没有这个单元，只是名字被引用过；脚本把 `list-units --all` 的每一行
  都当成了真实存在的单元。
- **修法**：报告里的每一处命中当场定性——是检查器的错就修检查器（这里：候选集不收
  `not-found` 的行），是预期就写成具名豁免并记进手册。
- **通用律**：常驻的非零读数和恒红一样，会把真命中淹掉。修检查器之前先查清命中的
  来路：第一次只加了个排除词，是读数里"候选非空、单元文件路径为空"这个对不上的
  字段引出了真正的原因。

### A9. 门外的检查拦不住任何东西

- **形状**：一段合并脚本里，门是测试的退出码（不过就不推送）。有人在门后顺手加了
  一行导入冒烟检查，因为引号写错而报错——脚本照常推送了：那一行没有接到门上。
- **修法**：脚本里的每一行检查要么接门（失败即中止），要么明写"仅记录、不拦截"。
- **通用律**：加了却不接门的检查，红了也没人停；它给出的只是"我检查过了"的感觉。

## B. 子进程、端口与服务

### B1. wrapper 双层执行会漏杀孙进程

- **形状**：引擎的可执行文件是"壳再 exec python"两层。`terminate()` 直接子进程只杀壳，
  python 进程带着 10GB 显存成了孤儿；两道验收门都是绿的，退出后查进程表才发现。
- **修法**：子进程放独立会话（`start_new_session=True`），停止时对整个进程组发信号
  （SIGTERM → 超时 SIGKILL）。
- **通用律**：起子进程的件，要对"退出后资源归零"立读数，不能只对"起得来"立读数。

### B2. 服务端口会静默迁移

- **形状**：推理服务的"找空闲端口"逻辑在目标端口被占时不报错，而是另挑一个端口；
  健康轮询挂在错误的端口上直到超时，真正的原因不可见。
- **修法**：起服前自己 bind 一次目标端口，占不住就大声失败。

### B3. 验收谓词要锚定被验对象

- **形状**：停服后"端口 bind 失败"是 TIME_WAIT 残留（真正的消费者带 `SO_REUSEADDR`
  不受影响）；停服后"free 低于阈值"是第三方模型回卡，不是泄漏。两处首验误红，
  都是谓词口径错，不是回收失败。
- **通用律**：验收读数先问"这个量里混了几方"；混了，就换只读自己那一方的谓词。

### B4. 健康绿 ≠ 后端就位

- **形状**：共享库树里新旧两版同名 CUDA 包混装，依赖旧版的库悬空；推理服务的 GPU
  后端加载失败**不报错**：健康检查绿、能出活，只是掉到了 CPU（慢十倍）。
- **修法**：起外部服务的验收锚资源侧读数——健康 + 进程表里有本件进程 + 一次真实生成。
  三件齐了才算起来。

## C. 实验纪律

### C1. 判决漏落表会在交接链上滚雪球

- **形状**：一个阶段标了"完成"但没走收尾门，判决行残留"待填"；下一个 session 接手时
  无法判断它是否真的验收过。
- **修法**：收尾门里"判决已落表"对每个波次都不可豁免。

### C2. 锚定件扩展时，锚形态的输出必须字节不变

- **形状**：脚本生成器只认一种已验证的形态；要支持新形态时，顺手改了公共路径，
  已验证形态的输出跟着变了。
- **修法**：扩展点显式留缝（新形态做成可选项），已验证形态的输出用单测逐字钉住。

### C3. 管线等价用锚带判据，不用绝对阈值

- **形状**：验证"新脚手架与旧流程等价"时，若设绝对阈值，会把复现波动误判成管线差异。
- **修法**：同数据同流程的历史读数就是标尺，落带即等价；带外先做配方要素逐项 diff。
- **延伸**：参数快照对锚逐项 diff，即使读数落带也要做——diff 本身是缺陷探测器
  （曾借它抓出一个模板开关被误传的问题）。单点等价后可按相邻列（容量档、数据臂）
  扩证，等价主张就从一次性读数升级为形态复现。

### C4. 外部判分依赖必须钉版本

- **形状**：以本地路径方式安装的外部工具只记目录不记版本；上游日更，重装即让判分器
  静默漂移。
- **修法**：PROVENANCE 记 commit；无记录时用文件指纹对历史提交比对来定位；
  重钉之后必须重跑锚带。

## D. 环境与数据

### D1. 共享 GPU：起跑前卸载可卸的第三方

- **形状**：需求线只对起跑瞬间负责。按需加载的第三方（如 embedding 模型）会在训练
  中途上卡触顶——首跑在第 3 步 OOM。
- **修法**：重载训练起跑前先卸载可卸的第三方，比等窗口可靠。

### D2. 开仓模板第一天就要带 .gitignore

- **形状**：新仓没有 .gitignore，适配器权重被提交进 git，仓库膨胀到几百 MB，
  最后不得不改写历史。
- **修法**：模板自带 .gitignore。真要改写历史，先做双保险：全量 bundle 留底
  **加上工作树拷贝**（filter-repo 会把被剥离的文件从工作树 reset 掉，只留 bundle
  会丢现场）。

### D3. 停第三方服务前，先落一份可执行的恢复脚本

- **形状**：为了腾显存临时停掉常驻服务；恢复时环境已经变了（见 A3、B4），
  靠一份边修边迭代的恢复脚本才恢复回来。
- **通用律**：破坏性/临时性的环境操作，先写恢复脚本再动手。

### D4. "跨仓可导入"要在起跑前可见

- **形状**：项目脚本用训练环境的解释器跑，而 labkit 没装进那个环境、也没设
  `PYTHONPATH`——脚本跑到一半才静默失败，发生过两次。
- **修法**：环境自检里加一项"该解释器能否 import labkit"，把跑中失败提前成起跑前读数
  （已固化为 `labkit doctor` 的一门）。
